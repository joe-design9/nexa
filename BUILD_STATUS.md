## So startest du Nexa
1. **Backend + Web:** `cp .env.example .env && docker compose up --build -d` – danach Web `http://localhost:3000`, API `http://localhost:4000`, MailHog `http://localhost:8025`, MinIO-Konsole `http://localhost:9001`. Demo-Daten einspielen: `docker compose exec api npm run db:seed` (Demo-Konten + Start-Invite-Codes stehen in der README). Neue Migrationen nicht vergessen: `docker compose exec api npm run db:deploy` (legt die Tabelle `PlatformInviteCode` an und ergänzt die Favoriten-Spalten `isFavorite`/`favoritedAt` an `Member`).
2. **Desktop-App (normal):** `apps/desktop/release/Nexa-Windows.zip` herunterladen, entpacken, `win-unpacked/Nexa.exe` starten. **Admin-Version:** `apps/desktop/release-admin/Nexa-Admin-Windows.zip`, darin `win-unpacked/Nexa Admin.exe`. Beim ersten Start erscheint der Nexa-Startbildschirm: **Server-URL** eingeben (voreingestellt `http://localhost:3000`) – das ist die Adresse der Web-Oberfläche deiner Nexa-Instanz; die Desktop-App lädt diese UI und verbindet sich mit deren API. Die URL wird gespeichert und kann später in den Einstellungen geändert werden. In der Admin-Version mit dem Admin-Konto `nexaadmin` / `NexaAdmin!2026` anmelden und unter „Plattform-Administration“ Invite-Codes erzeugen und verteilen.
3. **Installer selbst bauen (optional):** Auf Windows oder Linux mit installiertem Wine: `npm install && npm run dist:win -w @nexa/desktop` → erzeugt `Nexa-1.0.0-x64.exe` (NSIS-Installer) und `Nexa-Portable-1.0.0.exe`. Für die Admin-Version: `npm run dist:win:admin -w @nexa/desktop` → `Nexa Admin-1.0.0-x64.exe` + `Nexa-Admin-Portable-1.0.0.exe` in `release-admin/`.

### Bugfix 27.10. (Crash der eingeloggten Web-Ansicht – React-Fehler #185) – behoben und live verifiziert
- **Symptom:** Die Hauptansicht nach dem Login (`/app` bzw. Server-/Kanalansichten) stürzte mit React-Fehler **#185 „Maximum update depth exceeded“** ab („Application error: a client-side exception has occurred“); in der Konsole stand „The result of getSnapshot should be cached to avoid an infinite loop“, der Dev-Stack zeigte `forceStoreRerender`/`updateStoreInstance` aus einem passiven Effekt. Landing, `/login` und `/register` waren nicht betroffen – der Fehler trat nur in der eingeloggten Shell auf.
- **Ursache:** zustand v5 nutzt Reacts `useSyncExternalStore` **ohne Ergebnis-Cache**. Mehrere Selektoren lieferten mit einem literalen `|| []` bei noch nicht geladenen Store-Einträgen bei jedem `getSnapshot`-Aufruf eine **neue Array-Referenz**; React wertet das bei jedem Passiv-Effekt-Check als Änderung, erzwingt ein Re-Render und läuft in die Endlosschleife. Zuerst ausgelöst in `ChannelSidebar` (`apps/web/src/components/shell.tsx`: Kanäle/Kategorien eines Servers, dessen Detaildaten zum Render-Zeitpunkt noch nicht im Store waren); dieselbe fehlerhafte Stelle existierte in der Mitgliederliste (`members`/`roles`), in den Erstellen-Modals (Kanäle/Kategorien) und beim Voice-Status in der Channel-Page.
- **Warum erst jetzt sichtbar:** Der Fehler braucht echte Daten und ein echtes Timing: Es muss ein Server existieren, dessen Detaildaten (Kanäle/Mitglieder) beim ersten Rendern noch nicht im Store sind. Mit leerer Datenbank, ohne Login oder in Smoke-Tests ohne Seed-Daten trat er nicht auf – sichtbar wurde er erst im Live-Betrieb mit echter PostgreSQL, eingespielten Migrationen und Seed-Daten.
- **Fix:** Eine gemeinsame, referenzstabile Konstante `EMPTY_LIST` in `apps/web/src/lib/store.ts`; alle betroffenen Selektoren (Shell: Kanal-Sidebar, Erstellen-Modals, Mitgliederliste; Channel-Page: Voice-States) nutzen sie statt eines literalen `[]`. Kein Feature entfernt, keine sonstige Verhaltensänderung. Desktop-Code unberührt, Desktop-ZIPs unverändert.
- **Live-Verifikation (Sandbox mit echter DB):** Reproduktion vorher per CDP-Konsolenauslese im Electron-Fenster (eingeloggt als Demo-Nutzer `lena@nexa.local`): #185 + getSnapshot-Warnung mit Komponenten-Stack auf `ChannelSidebar`. Nach dem Fix: **0 Konsolen-Fehler, 0 Exceptions**; die Kanalansicht von „Nexa Gaming Hub“ zeigt Serverleiste (inkl. Favoriten-Sterne), Kanal-Sidebar, Chat-Verlauf und Mitgliederliste (visuell per Screenshot geprüft); auch `/app/channels/@me` fehlerfrei.
- **Build/Tests danach:** Production-Build wiederhergestellt (`npm run build` im Repo-Root: Shared + API + Web **fehlerfrei**, alle Routen generiert – der Dev-Server hatte `.next` überschrieben); `npm test` im Repo-Root erneut **126/126 bestanden** (74 Shared + 52 API).

## Bekannte Einschränkungen (ehrlich)
1. NSIS-Installer/Portable-Einzeldatei: nur wegen fehlendem Wine in dieser VM nicht gebaut – siehe Abschnitt oben (ZIP mit lauffähiger `Nexa.exe` liegt bei; Ein-Befehl-Fertigstellung dokumentiert).
2. Bot-Slash-Command-Definitionen in Redis statt Postgres (kein Schema-Model dafür angelegt).
3. OAuth-Nutzer und Bots erhalten ein Sentinel-Geburtsdatum (1970-01-01 / 2000-01-01), weil das Schema ein Datum verlangt und Provider keines liefern – im Code kommentiert.
4. Social Login ist erst nach Eintragen echter Provider-Credentials in `.env` aktiv (bewusst kein Fake-Flow).
5. Weiterleiten im Web-Client nutzt eine Kanal-ID-Eingabe (kein globaler Kanal-Picker-Endpunkt vorhanden).
6. Invite-Gate bei Social Login: greift nur, wenn OAuth auf der Instanz konfiguriert ist (echte Provider-Credentials in `.env`) – ohne Konfiguration bleibt es beim bisherigen ehrlichen `not_configured`-Verhalten; ein Live-OAuth-Durchlauf war in dieser Sandbox (keine Provider-Credentials, keine DB) nicht testbar, der Gate-Codepfad ist per Unit-Tests auf Service-Ebene verifiziert (`resolveOAuthAccount`).
7. Plattform-Invite-Codes stehen im Klartext in der DB – bewusst so, damit der Betreiber sie in der Admin-Version jederzeit wieder sehen und kopieren kann. Lesbar sind sie ausschließlich über die Admin-API mit Admin-Rolle (`AdminGuard`); es gibt keinen öffentlichen Endpunkt dafür.
8. NSIS-Installer/Portable gilt für die Admin-Version wie für die normale: In dieser VM nur als entpacktes Verzeichnis + ZIP gebaut (Wine fehlt) – Fertigstellung per `npm run dist:win:admin -w @nexa/desktop` auf Windows oder Linux+Wine.
9. Server-Favoriten haben (wie der Rest der API) keinen Live-E2E-Durchlauf mit echter DB in dieser Sandbox bekommen (kein Docker verfügbar) – verifiziert über strikte Builds, Unit-Tests mit gemocktem Prisma (echter PermissionsService darüber), Bundle-Nachweise und den Web-Smoke-Test. Favoriten-Sortierung der Serverleiste kombiniert serverseitige Favoriten mit der lokalen Drag-Reihenfolge des jeweiligen Geräts; die Drag-Reihenfolge selbst ist weiterhin nur lokal (localStorage) gespeichert, der Favoriten-Status dagegen serverseitig pro Konto.
10. Zweisprachigkeit: Die Desktop-Startbildschirme folgen der Systemsprache, nicht der in der Web-UI gewählten Sprache (die file://-Seiten haben eine andere Origin und keinen Zugriff auf deren localStorage/Cookie) – umschalten lässt sich die Sprache in der Web-UI selbst (Einstellungen/🌐-Knopf). API-Fehlermeldungen werden clientseitig über den Fehlercode übersetzt; bei einem Code ohne Wörterbuch-Eintrag erscheint die (deutsche) Server-Meldung. Inhalte (Namen, Nachrichten, Seed-Texte) sind Daten und werden nicht übersetzt.
11. Abzeichen-System: Automatisch vergeben werden nur EARLY_ADOPTER (Registrierung; die Zählung „erste 100“ umfasst alle Konten inkl. Seed-/Bot-Konten) und SERVER_FOUNDER (erster eigener Server). Alle anderen Abzeichen – auch BETA – vergibt ausschließlich ein Plattform-Admin (Admin-API/Admin-Version) oder der Seed; es gibt keine Fortschritts-/Aktivitäts-Automatik (z. B. zählt CHATTERBOX keine Nachrichten). Die Admin-Verwaltungs-UI wurde – wie schon die Invite-Verwaltung – per Build-Nachweis und API-Live-Test verifiziert, aber nicht klickend in der Admin-Desktop-Version durchgespielt: Das Linux-Electron-Testfenster in der Sandbox hat keine Desktop-Bridge, daher bleibt die Sektion dort (korrekt) ausgeblendet. Im Profil-Endpunkt `GET /users/:id` trägt das Feld `badges` aus Kompatibilitätsgründen weiterhin das alte Flags-Objekt (`{verified, bot}`); die Abzeichen-Schlüssel stehen dort in `badgeGrants` (kompakte Schlüssel-Arrays liefern die übrigen Endpunkte im PublicUser-Feld `badges`).
12. Onboarding-Tutorial: Die Spotlight-Hervorhebung hängt an `data-tour`-Ankern in Shell/Chat; Schritte, deren Element in der aktuellen Ansicht nicht existiert (z. B. Favoriten-Stern bei einem Konto ganz ohne Server, Nachrichtenfeld in der Freundesansicht), zeigen die Karte stattdessen zentriert über der abgedunkelten App – erklärt wird alles trotzdem. In den Einstellungen (Vollbild-Ansicht ohne Serverleiste/Sidebar) erscheinen beim manuellen Neustart alle Karten zentriert. Das Gesehen-Flag ist ein einziges Profil-Flag pro Konto (kein Fortschritt pro Schritt, kein „später fortsetzen“): Wer die Tour abbricht/überspringt, gilt als gesehen; ein begonnener, nicht beendeter Durchlauf startet nach einem Reload erneut von vorn, solange das Flag noch nicht gesetzt wurde (gesetzt wird es nur bei Beenden/Überspringen). Die Tour deckt die Web-UI ab (die Desktop-App lädt dieselbe UI); eigene Tutorial-Bildschirme der Desktop-App gibt es nicht.
13. Eingebackene Server-Adresse + PC-Hosting: Die ausgelieferten ZIPs enthalten bewusst **keine** `nexa-server.txt` und keine öffentliche Adresse – es gibt ohne Joels Hosting-Setup keine öffentliche Nexa-Instanz. Das Hosting-Kit lässt den Server auf Joels eigenem PC laufen: Er ist nur online, solange der PC läuft und online ist, und die feste Adresse muss Joel selbst per Tunnel (eigene Domain für Cloudflare Named Tunnel bzw. ngrok-Abo/Tailscale) bereitstellen; Quick-Tunnel-Adressen wechseln bei jedem Start und sind zum Einbacken ungeeignet. Ändert sich die feste Adresse, muss neu gebaken und ein neues Release hochgeladen werden. Die PowerShell-/Batch-Skripte des Kits konnten in dieser Linux-VM nicht ausgeführt werden (kein Windows/PowerShell) – verifiziert ist der Desktop-Mechanismus (CDP-Livetests), nicht der erste Skript-Lauf auf Windows.
